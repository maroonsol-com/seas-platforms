# Database architecture

Admin and Clinic use two separate Neon PostgreSQL databases. They do not share a schema, a migration history, a connection string, or a Drizzle configuration.

| Application | Working directory | Runtime URL | Migration URL | Target | Drizzle config | Schema | Migrations |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Admin | `admin/` | `DATABASE_URL` | `DATABASE_URL_UNPOOLED` | `APP_DATABASE_TARGET=admin` | `admin/drizzle.config.ts` | `admin/src/db/schema/` | `admin/drizzle/` |
| Clinic | `clinic-client/` | `DATABASE_URL` | `DATABASE_URL_UNPOOLED` | `APP_DATABASE_TARGET=clinic` | `clinic-client/drizzle.config.ts` | `clinic-client/src/db/schema/` | `clinic-client/drizzle/` |

The variable names match on purpose. Each application's `.env`, and later each Vercel project, supplies a different value. A migration command reads that application's `.env` and refuses to continue when `APP_DATABASE_TARGET` is anything else. A URL exported in the shell does not override the file.

## Connections

- Runtime reads use `@neondatabase/serverless` through Drizzle's Neon HTTP driver and `DATABASE_URL`.
- The configured runtime URLs are Neon **pooled** URLs. The HTTP driver can use them safely because each query is a short request and does not hold a Postgres session.
- Clinic tenant reads and writes use Drizzle's Neon WebSocket driver inside `withTenantTransaction()` or `withUserTransaction()`. That pool also uses `DATABASE_URL`. Its client cap is 5 when the URL is pooled and 2 when it is a direct URL, so a direct URL cannot exhaust the Neon compute connection limit. Idle clients close after 10 seconds.
- `DATABASE_URL_UNPOOLED` is the direct Neon URL and is used only by Drizzle Kit migrations. It was derived from the pooled URL by removing the pooler host marker, then checked against Neon. It reaches the same database as `DATABASE_URL`. The original `DATABASE_URL` values were not overwritten.
- A direct URL can also serve the HTTP driver. Do not point an uncapped pool at a direct Neon host.
- Drizzle Kit rejects a host that contains `-pooler`.
- `db:generate` and `db:check` do not open a connection. When the direct URL is still a placeholder, they receive a non-routable local URL only so Drizzle Kit can load its config. That URL is not written into SQL.
- `db:migrate` and `db:studio` require the direct URL and the matching target. They refuse placeholders before opening a connection.

## Commands

Run these from the repository root.

```bash
pnpm --filter @saas/admin db:generate
pnpm --filter @saas/admin db:check
pnpm --filter @saas/admin db:migrate

pnpm --filter @saas/clinic-client db:generate
pnpm --filter @saas/clinic-client db:check
pnpm --filter @saas/clinic-client db:migrate

pnpm db:boundaries
```

`db:generate` writes SQL into that application's `drizzle/` directory. `db:check` compares the Drizzle schema with the latest migration snapshot. `db:migrate` applies that application's files only. `pnpm db:boundaries` reads both SQL histories and fails if one contains the other application's tables, a float money type, or a connection string.

A custom migration is generated with the same wrapper, which strips the extra `--` pnpm inserts:

```bash
pnpm --filter @saas/admin db:generate -- --custom --name platform_integrity
pnpm --filter @saas/clinic-client db:generate -- --custom --name tenant_protections
```

Do not run a migration from one application during the other application's Vercel build. Production migrations are a separate reviewed step. The configured Neon databases have the migrations listed at the end of this document. Do not reset them and do not use schema push.

## Shared rules

- Primary keys are UUIDs generated by PostgreSQL.
- Foreign keys use `ON DELETE RESTRICT`.
- Tenant-owned Clinic rows carry `business_id`. Child rows that must stay inside the parent business use a composite foreign key `(parent_id, business_id) → parent (id, business_id)`.
- Money is `numeric(14, 2)`. Tax rates are `numeric(5, 2)`. Quantities are `numeric(12, 3)`. There is no `double precision` or `real`.
- Timestamps are `timestamptz`.
- Clinical, financial, audit, and stock rows are not deleted. Cancellation or voiding is a status. Draft invoice lines, draft prescription medicines, and draft purchase lines can still be removed while the parent is `draft`.
- `platform_business_id` on a Clinic business is a correlation UUID. It is not a foreign key into the Admin database. Admin `product_business_id` on provisioning is the same kind of correlation in the other direction.

## Admin schema

Twenty-two tables. This database has no patients, appointments, invoices, inventory, or clinic users. It does not enable row level security. Platform operators are a separate population from clinic users.

### Administrators

| Table | Purpose |
| --- | --- |
| `platform_permissions` | Global permission catalog. `key` is unique. |
| `platform_roles` | Named platform roles. `name` is unique. |
| `platform_role_permissions` | Role to permission. Primary key `(role_id, permission_id)`. Deleting a role removes its grants. Deleting a permission that is still granted is restricted. |
| `platform_administrators` | Platform operators. Email is unique. Optional display name, mobile, address, and profile image. Timezone defaults to `Asia/Kolkata` and locale to `en-IN`. Status and `disabled_at` record access. |
| `administrator_otp_challenges` | Hashed sign-in codes. The raw code is not stored. |
| `administrator_sessions` | Hashed session tokens. `revoked_at` ends a session. |
| `platform_administrator_roles` | Administrator to role. Primary key `(administrator_id, role_id)`. `assigned_by` references an administrator. All of those foreign keys restrict deletion. |

### Products

| Table | Purpose |
| --- | --- |
| `saas_products` | One row per product application. `slug` and `name` are unique. Status defaults to `inactive`. |
| `product_configurations` | One configuration row per product. Feature names and non-secret metadata. No database passwords. |
| `product_integration_configs` | One integration row per product. Provisioning and entitlement URLs. `secret_env_var` must match `^[A-Z][A-Z0-9_]*$` and stores an environment variable name, never the secret. |

### Businesses, plans, and billing

| Table | Purpose |
| --- | --- |
| `businesses` | Platform record of a customer business: legal and display names, owner contact, address, optional 15-character GSTIN, timezone, and status (`provisioning_pending`, `active`, `suspended`, `archived`). |
| `business_products` | Exactly one product per business (`business_id` is unique). A deferred constraint trigger requires the link at the end of the insert transaction. A second trigger blocks changing `business_id` or `product_id` and blocks deleting the link. |
| `subscription_plans` | Plans belong to one product. `(product_id, name)` is unique. `price` is `numeric(14, 2)` and must be zero or greater. Currency is a 3-character code, default `INR`. Billing cycles are monthly, quarterly, half-yearly, annual (`yearly`), and custom. Optional limits for users, branches, and storage. |
| `plan_features` | Entitlements for a plan. `(plan_id, feature_key)` is unique. `enabled` is boolean. `limit_value` is optional. |
| `business_subscriptions` | A business subscription. `starts_on` must be on or before `expires_on`. Partial unique index `business_subscriptions_one_open` allows one row per business while status is `trial`, `active`, `expiring_soon`, or `suspended`. |
| `subscription_events` | Append-only subscription history. Updates and deletes are rejected. |
| `manual_payments` | Recorded bank, UPI, cash, or other payments. `amount` is `numeric(14, 2)` and must be greater than zero. `idempotency_key` is unique. Status is `recorded`, `received`, or `voided`. Recording a payment does not renew a subscription by itself. Deletes are rejected. |

### Onboarding and audit

| Table | Purpose |
| --- | --- |
| `invitations` | Owner invitations. `token_hash` is unique. The raw token is not stored. Deletes are rejected. |
| `business_provisioning` | Provisioning status for a business, unique per business and per idempotency key. Status is `pending`, `in_progress`, `succeeded`, or `failed`. `product_business_id` is the Clinic business UUID after provisioning. It is not a foreign key. The requested plan and dates are stored here until the subscription is created. `attempt_count` is an integer. Deletes are rejected. |
| `platform_settings` | Key-value platform settings. The key is the primary key. Values are JSON. |
| `platform_audit_logs` | Platform audit trail. Optional administrator and business references. Updates and deletes are rejected. |
| `administrative_activity_logs` | Operator activity. Updates and deletes are rejected. |

These protections are in `admin/drizzle/0001_platform_integrity.sql`.

## Clinic schema

Forty-two tables. This database has no platform administrators, SaaS products, subscription plans, or manual platform payments.

### Tenancy

| Table | Purpose | Isolation |
| --- | --- | --- |
| `businesses` | Clinic business. `platform_business_id` is unique. Status is `active`, `suspended`, or `archived`. | RLS on `id`. A second SELECT policy, `businesses_member_visibility`, returns businesses where the current user has an active membership. |
| `users` | Product-wide accounts. Email is unique case-insensitively. A person can belong to more than one clinic. | No RLS. Login looks up one email before a business is chosen. Application code must not list users except through memberships. Deletes are rejected. |
| `permissions` | Global permission catalog. `key` is unique. | No RLS. No tenant data. |
| `roles` | Roles owned by one business. `(business_id, name)` is unique. | RLS on `business_id`. |
| `role_permissions` | Grants a catalog permission to a role inside one business. | RLS on `business_id`. Composite foreign key back to the role. |
| `business_memberships` | User membership. `(business_id, user_id)` is unique. Status is `invited`, `active`, `suspended`, or `removed`. | RLS allows the row when `user_id` is the current user or `business_id` is the current business. Writes require the business setting. |
| `membership_roles` | Roles assigned to a membership, both in the same business. | RLS on `business_id`. |
| `branches` | Branches of a business. Branch code is unique per business. | RLS on `business_id`. |
| `branch_memberships` | Which memberships work at which branch. | RLS on `business_id`. Composite foreign keys to the membership and the branch. |

### Clinical

All of these tables have `business_id`, RLS, and indexes for the business plus the parent record. Composite foreign keys keep a patient, doctor, branch, and appointment inside the same business.

| Table | Purpose |
| --- | --- |
| `patients` | Patient demographics and a patient number unique per business. Deletes are rejected. |
| `patient_medical_records` | Allergy, history, or note rows. Deletes are rejected. |
| `doctor_profiles` | One profile per user per business. Registration number is unique per business. Consultation fee is `numeric(14, 2)`. Optional branch. |
| `staff_profiles` | Non-doctor staff profile for a membership. Optional branch. |
| `doctor_schedules` | Weekly hours. Weekday is 0–6 and the end time must be after the start time. These rows can be replaced as the schedule changes. |
| `doctor_leave` | Leave dates. `ends_on` is on or after `starts_on`. Deletes are rejected. |
| `appointments` | `ends_at` is after `starts_at`. `doctor_id` is required. A `btree_gist` exclusion constraint, `appointments_doctor_no_overlap`, blocks overlapping ranges for the same doctor unless the status is `cancelled` or `no_show`. Deletes are rejected. |
| `consultations` | Draft or finalized clinical note, including follow-up date. A finalized row cannot be updated. Deletes are rejected. |
| `consultation_amendments` | Append-only correction text. Updates and deletes are rejected. |
| `vitals` | Recorded measurements with range checks. Updates and deletes are rejected. A correction is a new row. |
| `diagnoses` | Recorded diagnoses. Updates and deletes are rejected. |
| `prescriptions` | Draft or finalized prescription. Doctor name, qualification, and registration are copied onto the row so a later profile edit does not rewrite history. Finalized rows cannot be updated. Deletes are rejected. |
| `prescription_medicines` | Medicine lines. They can change only while the prescription is `draft`. |

### Billing

| Table | Purpose |
| --- | --- |
| `services` | Reusable billable services. Optional code is unique per business when present. `default_price` is `numeric(14, 2)`. Unit, tax classification, and tax rate are stored on the service. A service does not create stock movements. |
| `invoices` | Invoice number is unique per business. Drafts use a `DRAFT-` number. Finalizing calls `next_invoice_number()`, which reads `business_settings.invoice_prefix` and locks `invoice_sequences` for that business. Subtotal, discount, tax, total, amount paid, credit total, and balance are `numeric(14, 2)`. `credit_total` is the sum of issued credit notes and cannot exceed `total`. Balance must equal total minus amount paid minus credit total. A negative balance is customer credit, not a cash refund. Issued amounts, identity, terms, and the issuer snapshot, including the logo data URL, cannot change after the invoice leaves `draft`. `amount_paid`, `credit_total`, `balance`, and `status` remain updatable so payments and credit notes can be recorded. Deletes are rejected. |
| `invoice_items` | A product line references a product and a service line references a service, both in the same business. Each line snapshots the name, code, description, unit, quantity, unit price, discount, tax classification, tax rate, tax amount, and line total. PostgreSQL recalculates tax and the line total on insert and update. Lines can change only while the invoice is `draft`. |
| `invoice_sequences` | One counter per business. Concurrent invoice requests serialize on this row. |
| `payments` | Receipt number is unique per business and comes from `receipt_sequences` through `next_receipt_number()`. Methods are cash, UPI, card, bank transfer, and other. Amount is greater than zero. Idempotency key is unique. Deletes are rejected. |
| `refunds` | Refund against a payment. Amount is `numeric(14, 2)`. Deletes are rejected. |
| `credit_notes` | Issued or voided credit notes. Amount and tax are `numeric(14, 2)`. Only `issued` notes count toward `invoices.credit_total`. A credit note does not insert a refund and does not change the original invoice total. Deletes are rejected. |
| `credit_note_items` | Lines on a credit note. Deletes are rejected. |

### Inventory, purchasing, and records

| Table | Purpose |
| --- | --- |
| `inventory_categories` | Categories owned by one business. |
| `products` | Reusable catalogue item and inventory product. SKU is unique per business. Description, unit, sale price, purchase price, tax classification, and tax rate are stored here. Sale and purchase prices are `numeric(14, 2)`. Reorder level is `numeric(14, 3)`. |
| `stock_movements` | Append-only signed ledger. Quantity cannot be zero. Positive receives stock and negative issues it. On-hand quantity is the sum. There is no mutable balance column. Updates and deletes are rejected. A movement whose source is a service is rejected. |
| `suppliers` | Suppliers for one business. GSTIN is 15 characters or null. |
| `purchases` | Purchase documents. Status moves from `draft` to `ordered`, `received`, or `cancelled`. Deletes are rejected. |
| `purchase_items` | Lines can change only while the purchase is `draft`. |
| `supplier_payments` | Payments to suppliers. Amount is `numeric(14, 2)`. Deletes are rejected. |
| `expense_categories` | Category name is unique per business. |
| `expenses` | Amount is `numeric(14, 2)` and must be zero or greater. Deletes are rejected. |
| `file_metadata` | Metadata only. `storage_key` is unique. `byte_size` is a non-negative bigint. `product_key` must be `clinic`. Status `deleted` means the metadata was retired. It does not remove bytes, and bytes are not in this database. |
| `business_settings` | One settings row per business. Branding, GSTIN, invoice prefix, currency, due days, terms, footer, and an optional PNG or JPEG logo data URL stay on this row. Issued invoices copy the branding they need. |
| `audit_logs` | Append-only clinic audit metadata. Updates and deletes are rejected. |

`users`, `permissions`, `user_otp_challenges`, and `user_sessions` have no row-level security because sign-in happens before a business is chosen. The other 43 tables enable and force row-level security. `patient_sequences` and `receipt_sequences` are among those 43.

## Tenant isolation

1. Authenticate the user.
2. Load that user's membership from `business_memberships`. `resolveBusinessAccess()` in `clinic-client/src/server/tenant-access.ts` returns the membership's `business_id`. If the browser also sends a business id and it differs, access is denied. A missing membership is denied. The browser value is never used as the business id.
3. Open `withTenantTransaction(businessId, …)` or, before a business is selected, `withUserTransaction(userId, …)`.
4. Those helpers run `set_config('app.current_business_id', id, true)` and, when a user id is present, `set_config('app.current_user_id', id, true)`. The third argument makes the setting local to the transaction. It is cleared on commit or rollback, including when the WebSocket connection returns to the pool. Do not use session-level `SET`.
5. RLS policies compare `business_id` with `current_setting('app.current_business_id', true)`. The missing-ok form returns null when the setting is absent, and the comparison then fails, so a query without context sees no tenant rows.
6. `ALTER TABLE … FORCE ROW LEVEL SECURITY` applies the policies to the table owner. The Neon role in the connection string also has `BYPASSRLS`, and forced row-level security does not apply to a bypass role. Tenant transactions therefore run `SET LOCAL ROLE clinic_app`. That role cannot bypass row-level security and is not the table owner. The role change ends with the transaction.
7. Application authorization remains mandatory. Row-level security checks the business id the server placed in the transaction. `createDatabase()` uses the HTTP driver as the owner role, so it must not be used for tenant tables.
8. `users` and `permissions` have no row-level security. Login looks up one email before a business is chosen. User lists must go through memberships.

`role_permissions`, `membership_roles`, `branch_memberships`, and `doctor_schedules` can be deleted because they are assignments, not clinical or financial history. Everything listed above as rejected is enforced by triggers, not only by application code.
